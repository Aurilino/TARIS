# TARIS — симулятор хранения данных блокчейна

Код шага 3 (среда). Спецификация — [docs/30_step3_simulation_spec.md](docs/30_step3_simulation_spec.md); все документы работы — в папке `docs/`; папка проекта открывается в Obsidian как хранилище.

## Что готово

| Модуль | Пункт спецификации | Содержание |
|---|---|---|
| `taris_sim/config.py` | параметры, сценарии | Параметры по умолчанию, сценарии S0 и S2, хэш конфигурации |
| `taris_sim/rng.py` | общие случайные числа | Независимые потоки случайности по (зерно, тип потока, узел, ...) |
| `taris_sim/world.py` | 3.1, 3.4 | Операторы и узлы, скрытые кластеры, истинный риск, уход из сети, простои (Вейбулл или логнормальное), шоки или бури, тихие потери |
| `taris_sim/data.py` | 3.2 | Поток блоков, ёмкость узлов |
| `taris_sim/chain.py` | 3.3 | Микропрерывания, пинги, аудиты PDP, общая случайность эпох, пошаговый интерфейс `reset()` / `step()` |
| `taris_sim/ledger.py` | 3.6 | Сквозной прогон: размещение, события мира, тихие потери и их обнаружение аудитом, восстановление, журнал потерь, восстановлений и раскрытий, метрики (EAFDL, MTTDL, избыточность, трафик, недоступность) |
| `taris_sim/crisis.py` | 3.9 | Библиотека кризисов (буря, каскад, износ, массовый уход, уязвимость ПО, пожар), ложные тревоги, предвестники по каналам, версии ПО, исходы; сценарий S6 |
| `taris_sim/policy.py` | 4.1 | Интерфейс политики, равномерное размещение (нижняя граница) и оракул (верхняя граница) |
| `scripts/check_world.py` | 3.7 | Проверки мира: частоты, тяжесть, шоки, уход, тихие потери, воспроизводимость |
| `scripts/check_chain.py` | 3.7 | Проверки наблюдения: шум пингов и аудитов, доля аудитов при простое, ошибка измерения длительности, воспроизводимость `step()` |
| `scripts/check_crisis.py` | 3.7, 3.9 | Проверки кризисов (минимальные): частоты, доля предсказуемых, согласованность жизни узлов, общие случайные числа, воспроизводимость |
| `scripts/crn_hashes.py` | — | Побитовая сверка таблиц мира с эталоном при правках кода |
| `scripts/check_ledger.py` | 3.7 | Проверки учёта: независимый пересчёт потерь по журналу фрагментов, сохранение фрагментов, формула трафика, воспроизводимость прогона |
| `scripts/run_baselines.py` | — | Полный прогон одной политики в S2 с сохранением результата |
| `scripts/plot_world.py` | — | Графики A–D |
| `scripts/plot_chain.py` | — | Графики E (как сеть видит простой) и F (зачем нужна франшиза) |
| `scripts/plot_ledger.py` | — | Графики G (резерв информации объекта) и H (потери и затраты границ сравнения) |

Дальше: `export` и `viewer` (3.8), `adversary` (3.5), `validate` (3.7).

## Запуск (Windows 11, PowerShell)

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python scripts\check_world.py          # проверки мира
python scripts\check_chain.py          # проверки наблюдения
python scripts\plot_world.py figures   # графики A–D
python scripts\plot_chain.py figures   # графики E–F
python scripts\check_ledger.py         # проверки учёта (около минуты)
python scripts\check_crisis.py         # проверки кризисов в сценарии S6
foreach ($p in "uniform15","uniform13","oracle13") { python scripts\run_baselines.py runs $p }   # 1–3 минуты каждая
python scripts\plot_ledger.py runs figures   # графики G–H
```

## Устройство

- Единица времени — сутки (эпоха). Длительности простоев задаются в часах.
- Возраст в согласованном мире входит как `1 + age / 30` (в месяцах плюс один), чтобы избежать логарифма нуля.
- `beta_0` калибруется так, что средняя по сети частота страховых случаев равна `mean_event_rate` в обоих режимах мира.
- Простой, начавшийся во время другого простоя того же узла, сливается с ним.
- Микропрерывания генерируются в `chain` из потока `rng.MICRO` по каждому узлу (не зависят от политики).
- Пинги идут по сетке с шагом 5 минут и своей фазой у каждого узла; наблюдаемый простой — серия проваленных пингов.
- Добавлен параметр `ping_noise` — ложный провал пинга из-за шума сети (в спецификации шум был задан только для аудитов).
- Наблюдения зависят только от мира, поэтому строятся заранее; `step()` выдаёт их по эпохам.
- Целостность фрагмента при аудите проверяет `ledger`: только там известно, какие фрагменты лежат на узле.
- Политика принимает решения на границах эпох: восстановление запускается в начале эпохи и длится `repair_hours`.
- Аудит проверяет все фрагменты узла (как ежедневное доказательство хранения); тихая потеря обнаруживается на первом аудите при доступном узле.
- Простой дольше `T_rep` для сети равен утрате фрагментов узла, даже если данные на нём целы.
