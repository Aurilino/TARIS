# Интерфейсы защищённого хранения TARIS

> [[56_encrypted_manifest|Архитектура]] · [[57_threat_model_keys|Модель угроз]] · [[01_plan|Общий план]]

Дата: 03.11.2026. Статус: проект контрактов для однопользовательского прототипа. Структуры ниже — логические типы, а не готовый сетевой протокол или реализованный API. Криптографическая библиотека и байтовый профиль выбраны в [[59_crypto_file_profile]], локальный поднабор интерфейсов реализован — [[60_crypto_demo_results]]. Сетевой API и весь исходный контракт не реализованы. Реальные ключи и данные в примерах не приводятся.

## 1. Ответственность компонентов

| Компонент | Ответственность | Чего не получает |
|---|---|---|
| `Client` | Шифрование, проверка манифеста, декодирование, расшифрование, публикация версии | Не доверяет результату агента без проверки |
| `KeyStore` | Хранение ключа доступа; открытие и перепаковка оболочек | Не выдаёт ключ доступа агенту |
| `Agent` | Выбор узлов, организация загрузки, переносов и восстановления шифротекста | Ключи, открытый объект, полный открытый манифест |
| `BlobStore` | Хранение неизменяемых зашифрованных записей и фрагментов | Секретные ключи |
| `Locator` | Поиск текущих держателей фрагмента | Право менять идентичность и содержимое фрагмента |
| `TrustedHeadStore` | Получение доверенного состояния и атомарная смена актуальной версии | Не считается обычным недоверенным ответом агента |

Для первого прототипа `TrustedHeadStore` — локальный доверенный клиентский реестр с резервной копией. Проверяемый ончейн-реестр и синхронизация нескольких устройств в этот этап не входят. Старую резервную копию нельзя автоматически считать свежим состоянием; при отсутствии доверенной актуальной записи чтение в режиме «последняя версия» завершается ошибкой.

## 2. Общие типы и версии

`ObjectId` — непрозрачный идентификатор объекта, не производный от открытого содержимого. `BlobId` — идентификатор неизменяемой записи по её байтам и выбранному алгоритму хеширования. `FragmentIndex` — индекс строки избыточного кода. `KeyHandle` — локальная ссылка на ключ в хранилище, не значение ключа и не поле сетевого сообщения.

Различаются `data_version` (новое содержимое или повторное шифрование), `manifest_version` (новое описание сборки) и `head_revision` (любое опубликованное изменение, включая замену оболочки). Перенос неизменного фрагмента между узлами изменяет `Locator`, но не версии объекта и манифеста. Повторное шифрование всегда создаёт новую версию данных.

Все входящие записи проверяются по схеме, допустимым размерам, отсутствию повторяющихся полей, поддерживаемой версии формата и списку разрешённых алгоритмов. Неизвестный алгоритм не включает запасной небезопасный режим. Точные ограничения задаются при выборе формата.

## 3. Доверенный указатель `ObjectHead`

| Поле | Смысл |
|---|---|
| `schema` | `taris-object-head/1` |
| `object_id` | Идентификатор объекта |
| `head_revision` | Монотонная ревизия опубликованного состояния |
| `data_version`, `manifest_version` | Версии содержимого и манифеста |
| `manifest_blob_id` | Контрольный идентификатор зашифрованного манифеста |
| `envelope_blob_id` | Контрольный идентификатор оболочки ключа |

Клиент получает указатель из доверенного реестра до принятия манифеста. Изменение оболочки при плановой смене ключа доступа увеличивает `head_revision`, даже если манифест и содержимое прежние. Сравнение только номера манифеста недостаточно для этой операции.

`TrustedHeadStore.read(object_id) -> ObjectHead` возвращает доверенный указатель или ошибку. `compare_and_swap(object_id, expected_revision, new_head) -> ObjectHead` публикует состояние только при совпадении прежней ревизии. При первом сохранении ожидается отсутствие записи. Подмена недоверенным сетевым хранилищем не допускается без отдельного механизма подтверждения актуальности.

## 4. Оболочка ключа `KeyEnvelope`

Открытый заголовок: `schema = taris-key-envelope/1`, `object_id`, `data_version`, `manifest_version`, `manifest_blob_id`, `access_key_id`, `wrap_profile`, `nonce`. `access_key_id` — локатор ключа, не секрет. Зашифрованная часть содержит только ключ манифеста и его профиль использования.

Весь открытый заголовок включается в аутентифицируемый контекст вместе с различителем назначения `key-envelope`. Клиент сверяет идентификаторы и версии с `ObjectHead`, а контрольное значение всей оболочки — с `envelope_blob_id`. Подмена оболочки другой версией должна завершаться ошибкой.

Интерфейсы хранилища ключей:

```text
KeyStore.open_envelope(access_handle, expected_head, envelope) -> ManifestKeyHandle
KeyStore.seal_envelope(access_handle, manifest_key_handle, binding) -> KeyEnvelope
KeyStore.rewrap(old_access_handle, new_access_handle, head, envelope) -> KeyEnvelope
```

Перепаковка не считается отзывом ранее скопированных ключей. Открытые значения секретов не сериализуются в ответы агенту. Внутреннее взаимодействие `KeyStore` с криптографической библиотекой задаётся отдельно.

## 5. Манифест `EncryptedManifest` и его содержимое

Открытый заголовок `EncryptedManifest`: `schema = taris-encrypted-manifest/1`, `object_id`, `data_version`, `manifest_version`, `crypto_profile`, `nonce`. За ним находится аутентифицированный шифротекст манифеста. Полный заголовок и различитель назначения `manifest` входят в контекст проверки. В заголовке нет ключей, порядка фрагментов и списка держателей.

После проверки и расшифрования клиент получает `ManifestPayload`:

| Поле | Содержание |
|---|---|
| `schema` | `taris-manifest-payload/1` |
| `object_id`, `data_version`, `manifest_version` | Повторная привязка к ожидаемому объекту |
| `plaintext_length` | Размер исходного содержимого |
| `object_crypto` | Профиль шифрования объекта, nonce, ключ объекта; контекст связывает объект и версию данных |
| `coding` | Профиль кода, необходимое число фрагментов `k`, общее число `n`, параметры декодирования и дополнения |
| `ciphertext_length`, `ciphertext_digest` | Размер и контрольное значение восстанавливаемого шифротекста |
| `fragments` | Список `FragmentDescriptor`, без повторяющихся индексов |

`FragmentDescriptor` содержит `fragment_index`, `blob_id`, `byte_length`. Используемый алгоритм контрольного значения фиксируется профилем формата. `Locator` ищет держателей по `blob_id`; адреса узлов не являются доверенным описанием содержимого. Контрольное значение защищает фрагмент потому, что клиент получил его из проверенного манифеста.

Проверки клиента: положительные и согласованные `k` и `n`, ровно `n` допустимых описаний, уникальные индексы, допустимые длины и поддерживаемые профили. Проверка подлинности шифротекста объекта остаётся обязательной после декодирования: контрольная сумма не заменяет её.

## 6. Служебные данные агента

```text
PlacementRequest(request_id, fragment_descriptors, storage_constraints)
    -> PlacementReceipt
FetchRequest(request_id, fragment_descriptors, required_count, deadline, byte_limit)
    -> поток FragmentCandidate
RepairPlan(plan_id, fragment_descriptors, coding_profile, k, n,
           ciphertext_length, ciphertext_digest, storage_constraints)
    -> RepairReceipt
```

`PlacementReceipt` перечисляет идентификаторы фрагментов, держателей и результаты записи. Это служебное свидетельство, а не криптографическая гарантия будущего хранения. Публикация требует клиентской проверки чтением согласно выбранному протоколу.

`FragmentCandidate` содержит индекс, идентификатор, узел-источник и байты фрагмента. Клиент проверяет байты самостоятельно, учитывает только разные исправные индексы и при повреждении запрашивает замену до исчерпания лимитов. Заявлению агента «проверено» доверять недостаточно.

`RepairPlan` — разрешённая владельцем копия минимальных несекретных параметров ремонта: в нём нет ключа объекта, содержимого манифеста целиком и длины открытого текста. Наличие плана раскрывает группе обслуживания принадлежность фрагментов одному объекту. Это принятое ограничение базового варианта.

Для локального прототипа владелец передаёт план через доверенную конфигурацию. Перед использованием в сети потребуется аутентификация плана и разрешений на запись; механизм подписи/авторизации выбирается отдельно. Без неё агент не вправе менять клиентские доверенные записи.

Агент может пересоздать фрагмент с прежним индексом и ожидаемыми байтами, проверить его `blob_id` и обновить держателей. Для этого декодирует только шифротекст. Если требуется новый индекс, изменение кода или число описанных фрагментов сверх `n`, клиент должен выпустить новую версию манифеста и плана. Самостоятельная адаптация `n` политикой текущего симулятора ещё не интегрирована с этим криптографическим контуром.

## 7. Клиентские операции

```text
Client.store(plaintext, access_handle, storage_constraints) -> ObjectHead
Client.read_latest(object_id, access_handle) -> VerifiedPlaintext
Client.rotate_access(object_id, old_handle, new_handle) -> ObjectHead
Client.reencrypt(object_id, authorized_handle, new_access_handle) -> ObjectHead
```

`store` создаёт независимые ключи, шифрует объект, кодирует его, размещает фрагменты, шифрует манифест, запечатывает ключ манифеста и публикует указатель после проверок. Идентификаторы манифеста и оболочки вычисляются после получения их байтов: оболочка может ссылаться на манифест, а манифест не ссылается на свою оболочку. Циклической зависимости контрольных значений нет.

`read_latest` читает доверенный указатель, проверяет контрольные значения записей, открывает оболочку и манифест, получает исправные фрагменты, декодирует шифротекст, проверяет его длину и контрольное значение, затем выполняет аутентифицированное расшифрование. `VerifiedPlaintext` выдаётся только после полного успеха. Обновление указателя во время чтения не превращает старую версию в новую: перед завершением клиент повторно проверяет ревизию; при изменении возвращает `VERSION_CHANGED` и повторяет операцию в пределах лимита. Результат соответствует подтверждённой ревизии в момент заключительной проверки, а не обещанию отсутствия будущих изменений.

`rotate_access` открывает и перепаковывает ключ манифеста, меняет оболочку и ревизию указателя. `reencrypt` создаёт новую версию данных с новыми ключами, фрагментами и манифестом; сначала необходим доступ к прежнему содержимому либо его независимой копии. Потерянный ключ без копии не восстанавливается такой операцией.

## 8. Публикация и сбои

Последовательность публикации: неизменяемые фрагменты, проверка их доступности, манифест, оболочка, проверка чтения, атомарный переход указателя. До успешного перехода старая версия остаётся актуальной. Конфликт ревизии возвращается владельцу, а не перезаписывает конкурентное изменение.

`request_id` позволяет повторно проверить результат операции после тайм-аута. Повторная отправка готового неизменяемого шифротекста допустима. Повторное шифрование изменённого содержимого требует нового допустимого криптографического контекста и nonce по правилам выбранного алгоритма. Осиротевшие записи убираются отдельным процессом после проверки, что они не нужны опубликованным версиям или резервным копиям; автоматическое удаление в прототипе по умолчанию не выполняется.

## 9. Ошибки и журналирование

| Код | Значение и реакция |
|---|---|
| `KEY_UNAVAILABLE` | Нет ключа в локальном хранилище; предложить восстановление из копии |
| `AUTH_FAILED` | Проверка оболочки, манифеста или объекта не прошла; не выдавать содержимое. Неверный ключ и подмена не обязаны различаться |
| `UNTRUSTED_HEAD` | Нет доверенной актуальной записи; «последняя версия» не подтверждена |
| `VERSION_CONFLICT`, `VERSION_CHANGED` | Конфликт публикации или изменение во время чтения |
| `FORMAT_UNSUPPORTED`, `INVALID_RECORD` | Неподдерживаемый профиль или некорректная структура; отказ до обработки больших данных |
| `MANIFEST_UNAVAILABLE`, `ENVELOPE_UNAVAILABLE` | Недоступна необходимая служебная запись |
| `FRAGMENT_INVALID` | Неверные байты, длина или индекс; исключить кандидата и запросить другой |
| `INSUFFICIENT_FRAGMENTS` | Не получено `k` разных исправных фрагментов в заданных пределах |
| `LIMIT_EXCEEDED` | Превышен лимит размера, времени или попыток; завершить операцию |

Журнал содержит идентификатор операции, этап, обезличенный идентификатор объекта, версии, счётчики байтов и результат. Ключи, открытый текст, полный открытый манифест и секретные оболочки в расшифрованном виде не журналируются. Агент не получает подробные клиентские ошибки расшифрования: сетевой ответ не должен превращаться в доступный посторонним сервис проверки ключей.

## 10. Готовность к реализации

Библиотека, AEAD-профиль, кодирование, формат записей, алгоритм контрольных значений, правила nonce, лимиты и локальное хранилище выбраны в [[59_crypto_file_profile]] (03.11.2026); совместимость зависимостей и локальное чтение проверены, итоги — [[60_crypto_demo_results]]. Затем требуется демонстрация на реальных байтах с успешным чтением и отказами по [[57_threat_model_keys]]. Новые демонстрационные файлы должны быть отделены от потоков мира и прежних прогонов. До реализации интерфейсы не означают работоспособный криптографический протокол и не подтверждают устойчивость к Сибилле.
