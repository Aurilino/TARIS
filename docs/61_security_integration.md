# Защищённое чтение: связь с прогоном TARIS

> [[56_encrypted_manifest|Манифест]] · [[57_threat_model_keys|Угрозы]] · [[60_crypto_demo_results|Байтовый прототип]] · [[01_plan|План]]

03.11.2026. Реализован первый уровень интеграции: анализ по завершённому прогону и проверка выбранных снимков на настоящих зашифрованных байтах. Это отдельный слой оценивания истины, не новые признаки агента и не полная реализация `adversary`. Пользователь разрешил продолжать эту работу без промежуточных подтверждений.

## 1. Что подключено

- `taris_sim/security.py`: `SecurityReplay` читает историю фрагментов, держателей, владения и доступности из `RunResult`.
- `RunResult.security_report(scenario, queries)` возвращает отдельный `taris-security-report/1`. Старые `metrics()`, `disclosures` и `taris-log/2` не переопределены.
- `crypto_demo/replay.py`: `verify_snapshot` воспроизводит выбранное состояние держателей на настоящем шифротексте. Расшифрование и ключи остаются клиентскими.
- `scripts/run_security_demo.py`: воспроизводимый малый прогон, сценарий угроз, отчёт и байтовая сверка.
- `scripts/check_security.py`: проверки семантики, накопления копий, интервалов, неизменности исходного прогона и согласованности с байтами.

Отсутствие дополнительных зависимостей для обычного прогона сохраняется: `security_report` импортирует анализатор лениво; сам анализатор не импортирует криптографический прототип. Только проверка на байтах требует `requirements-crypto.txt`.

## 2. Уточнённая модель

Один пользователь, одна неизменяемая криптографическая версия каждого объекта. Фрагменты создаются, теряются, восстанавливаются и переносятся согласно настоящему журналу. Противник получает контроль над выбранным узлом или владельцем с заданного момента и сохраняет все скопированные индексы. Перенос одного и того же индекса не увеличивает число разных фрагментов.

Если компрометация началась после уничтожения или снятия старой копии по журналу, задним числом она не выдаётся противнику. Компрометация держателя предполагает доступ к его целым локальным данным даже при сетевом простое. Если данные объявлены утраченными моделью Ledger, позднее чтение физически оставшихся секторов не моделируется.

Манифесты и оболочки считаются опубликованными и копируемыми с момента создания объекта. Они скрывают ключи шифрованием. Поэтому компрометация ключа манифеста открывает содержащийся в нём ключ объекта; компрометация единственного неротированного ключа доступа даёт доступ к существующим и будущим манифестам этого пользователя. Отказы доступа к манифесту в сценарии относятся к текущему клиентскому чтению и не стирают копии у противника.

Разные `attacker` — независимые коалиции: их фрагменты и ключи не объединяются. Для сговора события относятся к одному `attacker`. Раскрытие возможно только когда одна коалиция накопила достаточно разных фрагментов и получила ключ объекта (непосредственно либо через манифест/ключ доступа). Порядок этих двух событий может быть любым.

Компрометация и недоступность ключа задаются сценариями отдельно от отказов узлов. По статистике простоев вероятность утечки ключа не оценивается. Криптографическая подделка без ключа не объявляется вероятностным событием мира: в байтовой части проверяется фактический отказ аутентификации.

## 3. Сценарий `taris-security-scenario/1`

Отдельный файл, не расширение существующего `taris-scenario/1`:

```json
{
  "schema": "taris-security-scenario/1",
  "events": [
    {"kind": "compromise_node", "t": 0, "attacker": "A", "node": 7},
    {"kind": "compromise_manifest_key", "t": 3, "attacker": "A", "obj": 0},
    {"kind": "manifest_unavailable", "t": 5, "obj": 0, "until": 6}
  ]
}
```

Номера в примере иллюстрируют формат; перед выполнением проверяется наличие объекта, узла и владельца в данном прогоне. Единица времени — сутки. Интервал недоступности включает `t` и не включает `until`. События и запросы ограничены фактически выполненным горизонтом, а не всей длиной конфигурации. Объект должен уже существовать к адресованному ему событию.

| Событие | Поля сверх `kind`, `t` | Смысл |
|---|---|---|
| `compromise_node` | `attacker`, `node` | Постоянный контроль узла |
| `compromise_owner` | `attacker`, `owner` | Контроль всех узлов владельца, включая будущие размещения |
| `compromise_object_key` | `attacker`, `obj` | Утечка ключа конкретного объекта |
| `compromise_manifest_key` | `attacker`, `obj` | Утечка ключа манифеста и доступного через него ключа объекта |
| `compromise_access_key` | `attacker` | Утечка единственного клиентского ключа доступа, без последующей ротации |
| `client_key_unavailable` | `obj`, `until` | Клиент временно не может использовать ключ для объекта |
| `manifest_unavailable` | `obj`, `until` | Клиенту недоступен манифест |
| `envelope_unavailable` | `obj`, `until` | Клиенту недоступна оболочка ключа |
| `deny_node` | `node`, `until` | Узел не отдаёт фрагменты клиенту |
| `corrupt_node` | `node`, `until` | Узел отдаёт повреждённые байты; такие фрагменты отбрасываются |

Для демонстрации потери ключа и служебных записей подготовлен `scenarios/security/manifest_key_loss.json`. Это не сценарий случайной частоты атак и не их статистическая калибровка.

## 4. Отдельные исходы и метрики

Для каждого запроса отчёт возвращает:

- число и индексы доступных целых фрагментов, а также исправных ответов после отказов и подмен;
- возможность клиентского чтения и список одновременных причин недоступности;
- для каждой коалиции — накопленные индексы, сбор шифротекста, утечку ключа и раскрытие открытого текста;
- первый момент накопления достаточного числа копий и первый момент раскрытия, если они наступили к запросу.

Сводка содержит число проверенных запросов, число неуспешных чтений и число уникальных объектов с наблюдавшимся сбором шифротекста и раскрытием текста. Это значения на заданной сетке запросов, а не непрерывные вероятности, годовые интенсивности или доверительные интервалы. Причины недоступности могут перекрываться; их нельзя безусловно складывать.

Старое поле «Раскрытий» сохраняет прежнюю пороговую трактовку. С новой метрикой раскрытия открытого текста оно непосредственно не смешивается. Крупные прогоны H5/H6 ещё не выполнены.

## 5. Реальные байты и границы проверки

Снимок использует синтетическое тестовое содержимое выбранного объекта. Оно шифруется и кодируется согласно начальному числу фрагментов. При чтении доступны только держатели и индексы, живые и доступные в момент запроса по журналу TARIS; сценарные отказы и подмены действуют поверх них. Проверки ключа/манифеста воспроизводятся удалением соответствующего тестового файла. Противник декодирует только накопленные индексы; ключ в проверку расшифрования подставляется исключительно при явно заданной компрометации.

Это доверенный тестовый стенд: извлечение ключа проверяющим кодом не является интерфейсом агента. Секреты временные и не записываются в отчёт. Временный каталог удаляется после проверки. Размер тестовых байтов не равен условному объёму блока симулятора; криптографические задержки и служебный трафик не включены в прежние экономические метрики.

Текущее изменение числа хранимых копий допустимо, пока индексы остаются в исходном наборе манифеста: миграция и восстановление не требуют менять инструкцию сборки. Добровольное снятие копии делает её недоступной, но не меняет схему кода. Появление нового индекса явно отклоняется: оно требует новой версии манифеста. Перекодирование, повторное шифрование и ротация внутри времени симуляции пока не моделируются, хотя операции ротации есть в отдельном прототипе.

## 6. Команды и результаты

```powershell
.venv\Scripts\python.exe scripts\check_security.py
.venv\Scripts\python.exe scripts\run_security_demo.py
.venv\Scripts\python.exe scripts\run_security_demo.py --attack-file scenarios\security\manifest_key_loss.json --times 1,2,3,4,5,6 --out runs\security\service_loss
```

Проверка прошла 9 групп, включая 8 снимков с реальным AES-GCM/RS. Малый мир: S0, зерно 17, 50 начальных узлов, 12 суток, один объект в сутки, код 3/5, равномерное размещение. Исходные таблицы результата и метрики после анализа не изменились; повторный прогон дал тот же хэш таблиц. Для этого короткого горизонта годовая EAFDL не определена и не используется как свидетельство надёжности.

В демонстрации по умолчанию три начальных держателя объекта 0 скомпрометированы с момента размещения. Ключ доступа скомпрометирован на сутках 2. На сутках 1 противник восстанавливает шифротекст, но не раскрывает текст; на сутках 3 раскрывает. Клиент читает объект в обоих снимках. Это сконструированная проверка необходимых условий, а не открытие предсказательной способности агента.

Отчёты: `runs/security/check_report.json`, `runs/security/demo/security_report.json` и `byte_checks.json`. Конфигурация и точный сценарий сохраняются рядом. Исходы и сценарии воспроизводимы, а криптографические ключи и шифротексты создаются заново генератором ОС.

Отдельный запуск файла `manifest_key_loss.json` на том же мире проверил шесть снимков. На сутках 1 / 3 / 5 клиент получил соответственно `KEY_UNAVAILABLE`, `MANIFEST_UNAVAILABLE`, `ENVELOPE_UNAVAILABLE`; на сутках 2 / 4 / 6 чтение восстановилось. Байтовая сверка совпала с моделью во всех шести случаях; отчёты — `runs/security/service_loss/`. Во всех этих снимках фрагментов хватало: причины отказа действительно относятся к ключу и служебным записям.

XML-схема `presentations/taris_agent_scheme.xml` дополнена третьей страницей с реализованным слоем анализа и сверки.

## 7. Оставшиеся работы

Первый уровень интеграции закончен. Полный `adversary` с набором доверия, ложными сигналами и адаптивными действиями, версии и ротация во времени симуляции, доступность реплик манифеста, стоимость служебных записей и проверка H5/H6 остаются отдельными работами. Новый слой не изменяет решения политики и потому сам по себе не доказывает преимущества TARIS над противником.

### Продолжение 03.11.2026

Базовый модуль `adversary` реализован и связан с SecurityReplay: Сибилла, коалиция, ложные заявления, тихие потери, одна смена имени и согласованный уход. Опциональная утечка ключа задаётся независимо. Проверки и ограничения — [[62_adversary]]. Полный адаптивный противник и многозёренная проверка H5/H6 остаются отдельными работами.
