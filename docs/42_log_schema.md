# Визуализация — схема журнала прогона (этап 1.1)

> [[00_tema|Тема]] · [[01_plan|План]] · [[02_student|Студент]] · ← [[41_viz_overview|Визуализация: общий план]] · [[40_viz_plan_B|Визуализация: реализация]]

Журнал прогона — договорённость между Python-симулятором и страницей-просмотрщиком. Python считает прогон и пишет журнал; страница его только проигрывает (вариант B, [[40_viz_plan_B|план реализации]]). Версия схемы — `taris-log/1`.

## Принципы

1. **Источник истины — симулятор.** В журнале нет ничего, что страница должна досчитывать «по модели». Страница только ищет по времени и рисует.
2. **Два взгляда.** Раздел `net` — то, что видит сеть и политика (пункт 3.3 и «Что видит политика» спецификации). Раздел `truth` — то, что знает только симулятор. Если удалить `truth`, журнал остаётся рабочим: просмотрщик показывает «взгляд сети». Это же проверяет `check_export.py`.
3. **Подробно — редкое, сводками — частое.** Отдельными записями пишутся события, которые важны по одному: реальные простои, уходы, регистрации, шоки, кризисы, тревоги, потери. Частые мелкие события (микропрерывания, шум пингов, аудиты) пишутся сводками по узлу и интервалу агрегации. Предвестник виден в них как рост частоты.
4. **Объекты — выборкой.** Подробно (каждый фрагмент, каждое восстановление и перенос) — для выборки объектов; по остальным — суммы по эпохам.
5. **Компактно и воспроизводимо.** Таблицы — столбцами, время — целыми минутами, перечисления — номерами из словаря, файл сжат gzip. Тот же прогон даёт побитово тот же журнал.

## Два мира

| Мир | Назначение | Параметры | Интервал агрегации |
|---|---|---|---|
| Основной | просмотрщик: карта, карточки, лента событий | S6, `n_initial_nodes=200`, `node_join_rate=0.12`, 10 дата-центров, 4 провайдера, 3 региона — около 200 узлов в сети одновременно | 1 сутки |
| Полный | сводные графики, проверка размера | S6 по умолчанию (около 1650 узлов за горизонт) | 7 суток |

Без поправки частоты регистраций (`node_join_rate=0.12` вместо 0,6) мир с 200 начальными узлами за три года вырастает до 850 узлов: регистрации рассчитаны на сеть в 1000 узлов.

## Представление данных

- **Файл:** `runs/<имя>.taris.json.gz` — JSON, сжатый gzip. Браузер распаковывает его встроенным `DecompressionStream("gzip")`, без библиотек. Для опубликованной страницы тот же файл встраивается в base64.
- **Таблица** — объект «столбец → массив»; все массивы одной таблицы одной длины. Строка таблицы — элементы с одним индексом.
- **Время** — целые минуты от начала горизонта:

$$
m = \mathrm{round}(t \cdot 1440)
$$

где:

- $m$ — время в журнале, целые минуты;
- $t$ — время в симуляторе, сутки (эпохи);
- $1440$ — число минут в сутках;
- $\mathrm{round}$ — округление до целого.

  Эпоха с номером $e$ — это сутки от $e$ до $e + 1$, то есть минуты от $1440 \cdot e$ до $1440 \cdot (e + 1)$.
- **Нет значения** (бесконечность, «ещё не закончился») — `-1`.
- **Перечисления** — номера строк из раздела `dict`: например, `dict.outage_kind = ["own", "shock", "storm", "crisis", "pre_short", "leave"]`, и в таблице хранится 0–5.
- **Узел, объект, кризис** — целые номера, как в симуляторе.

## Разделы верхнего уровня

| Раздел | Взгляд | Содержание |
|---|---|---|
| `schema` | — | строка `"taris-log/1"` |
| `meta` | — | описание прогона |
| `dict` | — | словари перечислений |
| `world` | сеть | структура мира: регионы, провайдеры, дата-центры |
| `nodes` | сеть | наблюдаемые признаки узлов |
| `net` | сеть | события и сводки, которые видит сеть |
| `policy` | сеть | решения политики: размещения, восстановления, переносы, тревоги |
| `objects` | сеть | выборка объектов: фрагменты, восстановления и переносы |
| `outcomes` | сеть | потери и раскрытия объектов |
| `daily` | сеть | метрики по эпохам |
| `truth` | истина | истинные признаки узлов, истинные простои, шоки, кризисы, предвестники, тихие потери |

Потери и раскрытия относятся к разделу сети: когда объект потерян, это видно всем. Причина потери — в `truth`.

### `meta`

| Поле | Тип | Смысл |
|---|---|---|
| `scenario` | строка | сценарий (`"S6"`) |
| `world_mode` | строка | `"matched"` или `"mismatched"` |
| `seed` | целое | зерно |
| `config` | объект | полная конфигурация (`Config` как словарь) |
| `config_hash` | строка | хэш конфигурации |
| `code_commit` | строка | коммит git, на котором сделан прогон |
| `policy` | строка | название политики |
| `horizon_days` | целое | горизонт в эпохах |
| `agg_days` | целое | интервал агрегации сводок, сутки (1 или 7) |
| `n_sample` | целое | размер выборки объектов |
| `metrics` | объект | итоговые метрики прогона (`RunResult.metrics()` и сводка `crisis_report()`) |

### `world`

| Таблица | Столбцы |
|---|---|
| `regions` | `id` |
| `providers` | `id` |
| `dcs` | `id`, `provider`, `region` |

Регион дата-центра — наблюдаемый признак (по IP), заявленный дата-центр узла — тоже. Истинный дата-центр узла в текущей модели совпадает с заявленным; если позже появятся ложные заявления (модуль `adversary`), истинный попадёт в `truth.nodes`.

### `nodes` (сеть)

| Столбец | Смысл |
|---|---|
| `id` | номер узла |
| `dc`, `provider`, `region` | заявленный дата-центр, провайдер, регион |
| `subnet` | подсеть /24 (номер из словаря `dict.subnet`) |
| `hw_claimed` | заявленный класс оборудования |
| `wallet` | кошелёк выплат (номер) |
| `join` | регистрация, минуты; `-1` — регистрация отменена кризисом (узел не пришёл) |

### `net` (сеть)

| Таблица | Столбцы | Что это |
|---|---|---|
| `outages` | `node`, `start`, `end`, `cls` | наблюдаемые простои длиннее франшизы $d$ (по пингам); `cls` — частичный ущерб или полная гибель (длиннее $T_{rep}$); у ухода из сети `end` — конец горизонта |
| `micro` | `node`, `bin0`, `counts` | сводка коротких наблюдаемых событий (не длиннее $d$: микропрерывания и шум пингов): для каждого узла — номер первого интервала и массив чисел событий по интервалам |
| `audits` | `node`, `bin0`, `fails` | сводка проваленных аудитов по интервалам (сколько аудитов было всего, страница считает по жизни узла: `audits_per_epoch` в сутки) |
| `versions` | `version`, `t` | выпуски версий клиента |
| `updates` | `node`, `version`, `t` | обновления узлов |

Регистрации видны из `nodes.join`, уходы — из `net.outages` (простой, который не закончился). Отличить уход от очень долгого простоя сеть не может — так и в журнале.

### `policy` (сеть)

| Таблица | Столбцы | Что это |
|---|---|---|
| `alarms` | `t`, `type`, `ctype`, `cluster`, `prob`, `horizon` | тревоги политики (все) |
| `alarm_episodes` | `type`, `ctype`, `cluster`, `t0`, `until`, `n` | эпизоды тревог (пункт 3.9); верность эпизода — в `truth.alarm_check` |
| `repairs` | `obj`, `t`, `r`, `traffic` | восстановления объектов выборки |
| `migrations` | `obj`, `idx`, `from`, `to`, `t`, `t_done`, `ok` | переносы фрагментов объектов выборки |

Решения политики публичны: размещение и восстановления записываются в смарт-контракт. Поэтому они в разделе сети.

### `objects` (сеть)

| Таблица | Столбцы | Что это |
|---|---|---|
| `sample` | `obj`, `created`, `n`, `lost` | объекты выборки: создание, число фрагментов при размещении, потеря (`-1` — не потерян) |
| `fragments` | `obj`, `idx`, `node`, `from`, `to`, `end` | фрагменты объектов выборки: где и когда лежал; `end` — причина ухода с карты размещения (признан утраченным по простою, тихая потеря по аудиту, перенос); `-1` — лежит до конца |

Выборка — каждый $N$-й объект (по умолчанию 50 объектов, равномерно по времени создания), как в `run_baselines.py`.

### `outcomes` (сеть)

| Таблица | Столбцы |
|---|---|
| `losses` | `obj`, `t` — все потерянные объекты |
| `disclosures` | `obj`, `owner`, `t` — все раскрытия |

### `daily` (сеть)

По одной строке на эпоху: `epoch`, `fragments` (хранится фрагментов), `objects_alive`, `lost_cum` (потеряно объектов нарастающим итогом), `repair_traffic`, `migration_traffic`, `repairs`, `migrations`, `alarms_active` (число действующих эпизодов тревог).

### `truth` (истина)

| Таблица | Столбцы | Что это |
|---|---|---|
| `nodes` | `id`, `owner`, `hw_true`, `lam_year` (истинная частота страховых случаев в год), `phi` (истинная вероятность полной гибели при простое), `leave` (истинный момент ухода), `leave_reason`, `cancelled` | истинные признаки узлов |
| `outages` | `node`, `start`, `end`, `kind`, `destroyed` | истинные простои длиннее $d$ с источником (собственный, шок, буря, кризис, предвестник) |
| `micro` | `node`, `bin0`, `counts` | истинные микропрерывания по интервалам (без шума пингов; часть короче интервала пинга сеть не видит) |
| `pre_micro` | `node`, `bin0`, `counts` | из них — предвестники кризисов |
| `shocks` | `ctype`, `cluster`, `start`, `end`, `destroyed`, `n_nodes` | шоки и бури кластеров (пункт 3.4) |
| `crises` | `id`, `type`, `ctype`, `cluster`, `tau`, `W`, `w0`, `end`, `predictable`, `false_alarm`, `parent`, `n_targets`, `n_hit`, `destroyed` | шкала кризисов и ложных тревог (пункт 3.9) |
| `crisis_targets` | `crisis`, `node` | узлы-цели каждого кризиса |
| `precursors` | `crisis`, `node`, `start`, `end` | окна предвестника у узлов с меткой $\xi_{i,m} = 1$ |
| `audit_windows` | `node`, `start`, `end`, `w0`, `tau`, `rho`, `crisis` | окна износа с повышенным провалом аудитов |
| `silent` | `node`, `t` | тихие потери (сеть узнаёт о них только по аудиту) |
| `crisis_report` | столбцы таблицы `crisis_report()` | потери и упреждение по каждому кризису |
| `alarm_check` | `correct` | верен ли каждый эпизод тревог (в том же порядке, что `policy.alarm_episodes`) |

## Ключевые кадры

План реализации (пункт 2.3) предполагал ключевые кадры для быстрой перемотки. В схеме v1 они не нужны:

- состояние узла в момент $t$ — двоичный поиск по его интервалам простоя;
- положение фрагментов объекта выборки в момент $t$ — фильтр по интервалам `[from, to)`;
- метрики в момент $t$ — строка `daily` с номером эпохи $\lfloor t \rfloor$, все накопленные величины там уже есть.

Так перемотка в любую точку не требует проигрывать журнал с начала, а журнал не хранит одно и то же дважды. Если на этапе 2 окажется, что на крупном мире поиск медленный, ключевые кадры добавляются в `taris-log/2` без изменения остальных разделов.

## Что не входит в v1

- **Граф связей** (сила связи пар узлов по эпохам) — этап 5 визуализации; раздел `graph` добавится в `taris-log/2`.
- **Оценки агента** (риск узлов, тариф, объяснения решений) — этап 7, после шага 5 основного плана; раздел `agent`.
- **Вмешательства пользователя** — этап 6; сами вмешательства — файл сценария, а журнал пересчитанного прогона описывает их в `meta.interventions`.

## Проверки (`scripts/check_export.py`, пункт 1.3)

1. Журнал соответствует схеме: все разделы и столбцы на месте, длины столбцов таблицы совпадают, номера перечислений в пределах словарей.
2. Сверка с прогоном: число потерь, раскрытий, тревог, кризисов, наблюдаемых и истинных простоев, уходов и регистраций в журнале совпадает с таблицами симулятора; суммы сводок совпадают с числом событий.
3. «Взгляд сети»: в разделах кроме `truth` нет полей истины (владелец, истинный класс, источник простоя, признак предвестника).
4. Воспроизводимость: два экспорта одного прогона побитово равны.
