## 1. Выбор библиотек

| Назначение | Выбор | Основание |
|---|---|---|
| Аутентифицированное шифрование | `cryptography`, класс `AESGCM` | Готовые операции шифрования и проверки тега; поддержка Windows |
| Защита локального ключевого файла паролем | `cryptography`, `Scrypt` и `AESGCM` | Пароль используется через KDF, а не непосредственно как ключ |
| Избыточное кодирование | `reedsolo`, `RSCodec` | Готовый код Рида–Соломона с восстановлением известных стираний; чистый Python без обязательной сборки расширения |
| Контрольные значения, случайность, записи | `hashlib.sha256`, `secrets`, `json`, `base64` стандартной библиотеки | Отдельные расширения не нужны |

Кандидаты для воспроизводимой установки: `cryptography==50.0.2`, `reedsolo==1.7.0`. Обе версии установлены в текущем Python 3.12; импорт и сквозная работа проверяются `scripts/check_crypto_demo.py`. Версии закреплены в отдельном `requirements-crypto.txt`; `pip check` не обнаружил конфликтов. Базовый `requirements.txt` симулятора не расширялся.

## 2. Профиль `taris-local-crypto/1`

- Шифрование объекта, манифеста, оболочки и локального ключевого файла: AES-256-GCM; ключ 32 байта, nonce 12 байт, тег 16 байт. Вызов `AESGCM.encrypt` возвращает шифротекст с присоединённым тегом; отдельно второй тег не добавляется.
- Объект, манифест и ключ доступа имеют независимые случайные ключи. Идентификатор объекта — 16 случайных байт, представленных 32 строчными шестнадцатеричными символами.
- Каждое новое шифрование содержимого или манифеста использует свежий ключ и свежий случайный nonce. Для многократного шифрования оболочек под одним ключом доступа клиент хранит использованные nonce и отклоняет повтор; операции с данным ключом выполняются последовательно одним клиентом. Копия ключа на втором устройстве не разрешает независимую запись. При восстановлении из резервной копии ключ доступа сначала ротируется для новых записей.
- Повторная отправка уже созданного неизменяемого шифротекста не является повторным шифрованием. При сбое незавершённый результат либо повторно отправляется как есть, либо полностью создаётся заново по правилам профиля.
- Контрольные значения: SHA-256. `BlobId` имеет вид `sha256:` и 64 строчных шестнадцатеричных символа. Имя файла содержит только сами 64 символа, без двоеточия — для совместимости с Windows.
- Пароль локального ключевого файла: UTF-8 без неявной нормализации и обрезки. KDF `scrypt`: salt 16 случайных байт, выход 32 байта, `n=131072`, `r=8`, `p=1`. Это выбранные параметры прототипа, а не универсальная оценка достаточной защиты пароля. Потребление памяти и время измеряются при реализации; автоматическое снижение параметров запрещено.
- Для каждой новой записи ключевого файла создаётся новый salt и nonce. Внутри шифруются ключ доступа, его идентификатор и версия. Пароль вводится скрыто, не передаётся аргументом командной строки и не хранится в сценарии.

В прототипе ключевой файл является зашифрованным переносимым контейнером, а не аппаратным хранилищем. Слабый пароль допускает офлайн-перебор; проверка стойкости паролей и интеграция с системным хранилищем Windows в этот шаг не входят.

## 3. Однозначное представление JSON

JSON кодируется в UTF-8 без BOM и завершающего перевода строки: `json.dumps(value, ensure_ascii=True, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("utf-8")`. Это локальный профиль сериализации, не заявление о реализации международного стандарта канонического JSON.

Разрешены объекты с известными именами полей, списки, строки ASCII, булевы значения, `null` там, где разрешён схемой, и неотрицательные целые до 9007199254740991. Числа с плавающей точкой, дубли ключей и неизвестные поля отклоняются. Парсер сначала проверяет размер файла, затем структуру и ограничения глубины. Для версии 1 глубина вложенности не более 12.

Бинарные поля JSON кодируются стандартным Base64 с обязательным padding. Пробелы и альтернативное кодирование не принимаются; декодер проверяет точную ожидаемую длину. Перепаковка содержимого JSON меняет идентификатор файла: SHA-256 берётся от точных сохранённых байтов.

В контейнерах шифрования есть ровно два верхних поля: `header` и `ciphertext_b64`. Контекст AEAD — сериализованный тем же способом объект `{"purpose": <назначение>, "header": <полный заголовок>}`. Назначение одно из `object`, `manifest`, `key-envelope`, `local-keystore`. Заголовок не содержит самого шифротекста и собственного `BlobId`.

Для объекта заголовок содержит `schema`, `profile`, `object_id`, `data_version`, `nonce_b64`. Его копия хранится внутри манифеста в `object_crypto` вместе с ключом объекта. Кодируются только байты шифротекста с тегом, не JSON/Base64-представление. Манифест хранит `ciphertext_length` и SHA-256 именно этих байтов.

Заголовки манифеста и оболочки соответствуют [[58_manifest_interfaces]]. Поля профилей шифрования в версии 1 имеют единственное допустимое значение `AES-256-GCM`. Заголовок оболочки связывается с `manifest_blob_id`; манифест не ссылается на свою оболочку. Профиль хеширования — `SHA-256`.

## 4. Фрагменты `taris-rs-shards/1`

Для демонстрации по умолчанию `k=10`, `n=13`; разрешены значения `1 <= k < n <= 32`. Это лимит маленького прототипа, а не ограничение математической модели TARIS. Профиль кода: `RSCodec(nsym=n-k, nsize=n, fcr=0, prim=0x11d, generator=2, c_exp=8)`.

Шифротекст с тегом дополняется нулевыми байтами до длины, кратной `k`, затем делится на `k` последовательных равных блоков. Для каждой позиции внутри блоков берутся `k` байт, кодируются `RSCodec` в `n` символов и раскладываются в `n` фрагментов по индексам. Получается систематическое кодирование: первые `k` фрагментов соответствуют блокам дополненного шифротекста, остальные содержат проверочные символы.

При чтении отсутствующие или отвергнутые по контрольному значению фрагменты отмечаются как известные стирания. Декодер восстанавливает каждую позицию, соединяет первые `k` блоков в исходном порядке и отбрасывает дополнение по проверенной `ciphertext_length`. Окончательная проверка AEAD обязательна. Исправление неопознанной злонамеренной порчи только средствами RS не считается защитой подлинности.

Индекс и параметры кода находятся в проверенном манифесте; файл фрагмента содержит только бинарные байты. Переименование файла не меняет его индекс в манифесте. Размер каждого фрагмента одинаков, а `blob_id` проверяется по фактическим байтам. Для повреждённого фрагмента запрашивается другой кандидат; если исправных разных индексов меньше `k`, чтение завершается ошибкой.

Библиотечный RS-код не реализуется заново: собственная часть — только раскладка байтов по фрагментам и обратная сборка. Восстановление из любого допустимого набора `k` фрагментов требует отдельной проверки реализации. Для маленького набора `k=3`, `n=5` проверяются все подмножества, для `10/13` — все сочетания трёх потерянных фрагментов и случаи меньших потерь.

## 5. Каталог файлов

```text
<каталог демонстрации>/
  storage/
    blobs/<64 hex>.bin       бинарные фрагменты
    records/<64 hex>.json    зашифрованные манифесты и оболочки
    locator.json            недоверенная карта держателей
  client-private/
    head-store.json         доверенные указатели актуальных версий
    keystore.json           зашифрованный ключ доступа и состояние nonce
  recovery/                 отдельная копия для демонстрации восстановления
  events.jsonl              обезличенный журнал операций без секретов
```

Это структура для изолированного тестового каталога. Реальную резервную копию ключа нельзя считать независимой, если она хранится рядом с основным файлом на том же устройстве. Тестовые ключи не используются для настоящих данных и не публикуются вместе с результатами демонстрации.

Записи `ObjectHead` имеют схему из [[58_manifest_interfaces]]. Доверие к `head-store.json` обеспечивается границей локального клиента и правами файловой системы; сам JSON не доказывает актуальность. Запись через временный файл и атомарную замену, с блокировкой одного писателя. Противник с правом изменения доверенного каталога выходит за принятую границу защиты. Локальный реестр откатов не заменяет независимый доверенный источник для нового устройства.

## 6. Лимиты первого прототипа

Один исходный объект — до 1 МиБ; один JSON-контейнер — до 256 КиБ; не более 32 описаний фрагментов. Ограничение файла проверяется до разбора и выделения больших буферов. Не более двух ответов от разных держателей для одного индекса за одну попытку чтения; общий объём ответов не превышает 64 МиБ. Лимит попытки чтения — 30 секунд с проверкой между операциями; это не гарантия принудительного прерывания зависшего системного вызова. В первой демонстрации используются только локальные файлы, без сетевых запросов.

KDF-параметры заголовка сверяются с единственным допустимым профилем до запуска KDF: файл не может потребовать произвольный объём памяти. Уникальность nonce, сохранение состояния после сбоя и отказ при исчерпании лимитов проверяются отдельно. Для оболочек в реализации установлен лимит 1000 шифрований одним ключом доступа, затем требуется ротация. Первоначальные 100000 снижены, чтобы зашифрованный JSON со списком nonce помещался в лимит 256 КиБ. Статистика защитных операций не использует потоки `rng` мира: секреты генерируются через криптографический генератор ОС и не воспроизводятся зерном симуляции.

## 7. Что проверяется следующим шагом

После подтверждения автора реализованы изолированная запись и чтение реальных байтов. Проверки потерь, подмены, неверного ключа, восстановления из копии, отката относительно доверенного указателя и ротации собраны в `scripts/check_crypto_demo.py`; машинный отчёт — `runs/crypto_demo/check_report.json`. Замеряются время и объём для малого объекта. Не реализованы сетевой транспорт, служба Locator, журнал events.jsonl и интеграция с политиками TARIS; ручной запуск — `scripts/run_crypto_demo.py`. Встраивание в TARIS — самостоятельный последующий шаг.
