# I6 — причинный replay служебной очереди

12ноября2026. Все24исполнения103/close сохранены в `series_i6_replay/`, повторный физический/транспортный и временной аудит пройден. Все6контролей совпали с I5.1. `check_queue_control.py` независимо проверил ресурсы, стоимость и запас разных номеров. Это открытый диагностический мир, не независимая оценка эффективности.

В контролируемом примере выявлены два препятствия: полностью занятая repair-заявками очередь не принимает proof; принятый proof не проходит за активным ожиданием источников. Только совмещение резерва одного места и proof-обхода решает этот конкретный пример. Никакие физические данные не возвращаются в карту без стандартной проверки.

На случайном диагностическом мире хвост Classic/G/Hybrid:

| Правило | Быстрый канал | Медленный канал |
|---|---|---|
| исходное | 8/8/8 | 8/8/8 |
| только резерв места | 8/8/8 | 8/8/8 |
| только обход чтения | 8/0/8 | 8/8/8 |
| оба правила | 0/0/0 | 7/8/7 |

Потерь0во всех режимах, поэтому этот replay не доказывает уменьшение безвозвратных потерь. Улучшились подтверждённая карта и восстановленный запас: например, у быстрого Classic время ниже n=4 снизилось с480,618до64,713объекто-суток. Объём передачи вырос с1,51до42,958, учтённые расходы — с9,119до15,348. Бездействие было дешевле, но сохраняло дефицит резерва. Неизвестные будущие обязательства не обнулены.

У медленного G обнаружено дополнительное препятствие: восьмое место занято proofnode21, не относящимся к ожидающемуobj1. Адресный выбор его не запускает, нужный proof не принимается. Это основание для отдельного I6.1, а не для изменения завершённых файлов I6.

Сохранены `queue_evaluation_i6/results.json`, `RESULTS.md`, `verification.json`. Новые паузы чтения проверяются без фиктивного полного буфера. Девять новых тестов и полная проверка168тестов на этапе I6 пройдены. Аудитор I6.1 дополнительно обрабатывает законное совпадение времени выдачи сервера и начала read-wait при нулевой подготовке; исходные данные I6 с прежним аудитором не переписываются.
